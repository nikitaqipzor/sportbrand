# Задача: энциклопедия 918 упражнений → JSON-контракт

Исполнитель: отдельный агент / вторая ИИ. Ветка `content/exercise-db`, зона — только папка `content/`.

## Зачем это нужно

В приложении есть раздел «Энциклопедия» (в веб-прототипе это экраны 13–15: Каталог, Упражнение, Техника), но наполнять его нечем: единственный источник — Word-документ, из которого приложение читать не может. Без структурированной базы упражнений не работает ни подбор тренировки, ни фильтр по оборудованию, ни экран техники, ни прогрессии/регрессии.

Это самый крупный кусок работы, не требующий программирования, и он полностью независим от кода.

## Границы

**Зона исполнителя:** только `content/**`.

**Не трогать:** `source/**` (веб-прототип, мобильный клиент, Go API), `docs/ROADMAP.md`, `.github/**`, `product-materials/**` (входные данные, только чтение).

Ветка отдельная, файлы не пересекаются ни с одной другой зоной — конфликтов при слиянии быть не может.

## Входные данные

| Файл | Что внутри |
| --- | --- |
| `product-materials/Единая_энциклопедия_упражнений_спорт_918(2).docx` | 918 упражнений в 34 разделах, 7 колонок: название, основная нагрузка, оборудование, уровень, ключ техники, формат объёма |
| `product-materials/exercise_master_template_app_v1.docx` | Мастер-шаблон карточки v1.1 — **обязателен к соблюдению**, задаёт целевую структуру |

Мастер-шаблон прямо формулирует цель конвейера: *«Word-мастер → версионированный JSON-контракт → мобильное и веб-приложение»*.

## Что уже известно из разбора исходника

Мастер-шаблон содержит диагностику, повторять её не нужно:

- 918 записей, 34 тематических раздела, номера 1–918 идут последовательно;
- **890 уникальных названий и 28 повторяющихся** — связывать через `variant_of`, а не удалять;
- **289 вариантов описания нагрузки** и **89 строк оборудования** — требуют справочников машинных кодов;
- пошаговая техника, типичные ошибки, противопоказания, медиа и статус экспертной проверки **в исходнике не выделены** в отдельные поля.

## Структура карточки: 7 блоков

Ключи в фигурных скобках — машинные имена из мастер-шаблона, их и надо использовать.

| Блок | Поля |
| --- | --- |
| **A. Идентификация** | `EXERCISE_ID`, `LEGACY_NUMBER`, `SLUG`, `SCHEMA_VERSION`, `CONTENT_VERSION`, `CONTENT_LOCALE`, `NAME_RU`, `NAME_EN`, `ALIASES`, `VARIANT_OF`, `PUBLICATION_STATUS` |
| **B. Классификация и анатомия** | `SPORT`, `SECTION`, `CATEGORY`, `MOVEMENT_PATTERN`, `GOAL_TAGS`, `EQUIPMENT`, `DIFFICULTY`, `PRIMARY_MUSCLES`, `SECONDARY_MUSCLES`, `JOINTS`, `LATERALITY` |

| **D. Программирование** | `VOLUME_TYPE`, `SETS_MIN/MAX`, `REPS_MIN/MAX`, `DURATION_MIN/MAX_SECONDS`, `DISTANCE_MIN/MAX_METERS`, `CYCLES_MIN/MAX`, `REST_SECONDS`, `INTENSITY_TYPE`, `INTENSITY_MIN/MAX`, `STOP_CONDITION` |

## Правила, заданные шаблоном

**Три независимых статуса.** `publication_status` отвечает за видимость записи, `review_status` — за экспертную проверку, `media_status` — за готовность визуальных материалов. Публикация разрешена только при `publication_status=ready` **и** `review_status=approved` **и** `media_status=approved`. Схема обязана это выражать, а валидатор — проверять.

Жизненный цикл публикации: `draft` → `in_review` → `ready` → `published` → `archived`.

**Правило вариантов.** Одностороннее выполнение, другой хват, положение тела или оборудование оформляются отдельной записью **только если** меняются техника, безопасность, диапазон или тренировочный акцент. Связь — в `variant_of`.

**Никакой фильтрации по свободному тексту.** Приложение фильтрует по машинным кодам, пользователю показываются локализованные названия. Отсюда обязательность справочников.

## Что сделать

1. **Схема** — `content/schema/exercise.schema.json` (JSON Schema), все 7 блоков как независимые поля. Обязательные поля помечены звёздочкой в шаблоне.
2. **Справочники** — `content/dictionaries/`: виды спорта, разделы, оборудование (89 строк исходника → коды), мышцы, суставы, паттерны движения, цели, уровень (`beginner` / `intermediate` / `advanced`), сторона. Каждый код — с локализованным названием RU.
3. **Экспорт** — `content/exercises/`, по файлу на раздел. Стабильные `EXERCISE_ID` и `SLUG`, `LEGACY_NUMBER` 1–918 сохранён.
4. **Дубли** — 28 повторяющихся названий связать через `VARIANT_OF` по правилу выше. Автоматически не удалять.
5. **Незаполненное помечать, а не выдумывать.** Полей `EXECUTION_STEPS`, `COMMON_ERRORS`, `STOP_SIGNS`, `CONTRAINDICATIONS`, медиа и статусов проверки в исходнике нет. Завести в схеме, оставить пустыми со статусом `draft`. **Придуманная методика безопасности хуже отсутствующей** — по ней люди будут тренироваться.
6. **Валидатор** — `content/validate.mjs` на `node:test`: схема соблюдена, `EXERCISE_ID` уникальны, все коды существуют в справочниках, `VARIANT_OF` указывает на существующую запись, правило трёх статусов не нарушено, сумма упражнений по разделам равна 918.
7. **README** — `content/README.md`: как устроен контракт, как добавить упражнение, как прогнать валидатор.

## Критерий готовности

`node content/validate.mjs` проходит, и по любому из 918 упражнений можно получить карточку, не открывая DOCX.

## Чего не делать

Не писать код приложения, не трогать API, UI и схему БД. Не заполнять поля техники и безопасности «правдоподобным» текстом. Только данные, справочники и их валидация.
